1. First: understand the big picture

Before writing code, I want you to have this mental model:

                    Browser
                       │
             ┌─────────┴─────────┐
             │                   │
        IndexedDB              OPFS
             │                   │
        Metadata              Actual files
             │                   │
       ┌─────┴─────┐       ┌─────┴─────┐
       │           │       │           │
     name        size    video.mp4   image.png
     type        date    document.pdf
     path        id      ...

Think of them as two different storage systems.

IndexedDB

Good for structured data:

File ID:       123
Name:          lecture.mp4
Size:          150 MB
Type:          video/mp4
Created:       ...
OPFS path:     /files/123/lecture.mp4
OPFS

Good for the actual file:

/files/
    123/
        lecture.mp4
    124/
        presentation.pdf
    125/
        image.png

So:

IndexedDB tells your application what exists. OPFS contains the actual file data.

That's the fundamental idea I want you to understand first.

2. Why don't we just put everything in IndexedDB?

This is an important question.

IndexedDB can store binary data such as Blobs.

For example:

const file = new Blob([...]);

await db.put("files", {
    name: "video.mp4",
    data: file
});

So you might ask:

Why do we need OPFS?

Because OPFS is specifically designed around file-like storage and efficient file operations.

Imagine you have:

video.mp4 = 2 GB

and your application needs to:

write
read
modify
stream
process
delete

OPFS gives you a filesystem-like abstraction.

You can work with:

directories
files
file handles
file streams
random access
synchronous access in workers

This becomes especially useful for applications such as:

video editors
audio editors
image editors
browser IDEs
offline applications
large file processing
caching
local databases
screen recording applications

And that last one should be especially relevant to you because you have already encountered screen recording/local file handling in your work.

3. What exactly is OPFS?

OPFS means:

Origin Private File System

Let's break that name down.

Origin

An origin is roughly:

scheme + host + port

For example:

https://example.com

and

http://localhost:3000

are different origins.

Private

The filesystem belongs to that website/origin.

For example:

https://myapp.com

can have its own OPFS storage.

Another website:

https://otherapp.com

cannot simply access it.

File System

It behaves somewhat like a filesystem:

root
 ├── videos
 │    ├── video1.mp4
 │    └── video2.mp4
 │
 └── documents
      ├── file1.pdf
      └── file2.pdf

But this is not your Ubuntu filesystem.

JavaScript cannot simply do:

open("/home/indura/video.mp4");

Instead, the browser provides APIs to interact with the origin's private filesystem.

4. What exactly is IndexedDB?

IndexedDB is a browser database.

It is a:

key-value/document-oriented database built into the browser.

You can store objects like:

{
    id: "abc123",
    name: "lecture.mp4",
    size: 10485760,
    type: "video/mp4",
    createdAt: 1720000000
}

You can then retrieve them later.

Conceptually:

IndexedDB
│
└── Database
     │
     └── Object Store
          │
          ├── record
          ├── record
          ├── record
          └── record

The terminology is important.

5. IndexedDB terminology

You will frequently see these terms in real code.

Database

For example:

MediaManager
Object Store

Similar to a table conceptually.

For example:

files

Inside:

files
├── file1
├── file2
├── file3
└── file4

But don't think of it as exactly the same as a SQL table.

IndexedDB isn't PostgreSQL.

Key

Every record has a key.

Example:

id: "8f3a..."
Index

An index allows efficient searching.

For example:

files

might have:

primary key → id

index → name
index → type
index → createdAt

Then you could search:

all video files

without manually checking every record.

7. Let's start with OPFS itself

Before React, let's understand the raw browser APIs.

Create a basic HTML page:

<!DOCTYPE html>
<html>
<head>
    <title>OPFS Test</title>
</head>
<body>

<script>
    async function testOPFS() {

        const root = await navigator.storage.getDirectory();

        console.log(root);
    }

    testOPFS();
</script>

</body>
</html>

The important line is:

const root = await navigator.storage.getDirectory();

This gives you the root directory of OPFS.

Think:

OPFS
└── root
8. Creating a directory

We can create:

files/

using:

const root = await navigator.storage.getDirectory();

const filesDirectory = await root.getDirectoryHandle(
    "files",
    { create: true }
);

Now conceptually:

OPFS
└── files/

The important part:

{ create: true }

means:

Create it if it doesn't already exist.

Without it, attempting to access a missing directory can fail.

9. Creating a file

Now:

const fileHandle = await filesDirectory.getFileHandle(
    "hello.txt",
    { create: true }
);

Now:

OPFS
└── files/
     └── hello.txt

Notice something important.

We don't directly manipulate:

"/files/hello.txt"

Instead we get a:

FileSystemFileHandle

That handle represents the file.

10. Writing to the file

Now:

const writable = await fileHandle.createWritable();

await writable.write("Hello from OPFS!");

await writable.close();

This is a very important pattern:

file handle
     ↓
create writable
     ↓
write
     ↓
close

Full example:

async function writeFile() {

    const root = await navigator.storage.getDirectory();

    const directory = await root.getDirectoryHandle(
        "files",
        { create: true }
    );

    const fileHandle = await directory.getFileHandle(
        "hello.txt",
        { create: true }
    );

    const writable = await fileHandle.createWritable();

    await writable.write("Hello from OPFS!");

    await writable.close();

    console.log("File written");
}

writeFile();
11. Reading the file

Now we want to read:

hello.txt

We get the handle again:

const fileHandle = await directory.getFileHandle("hello.txt");

Then:

const file = await fileHandle.getFile();

Now file is a browser File object.

We can read it:

const text = await file.text();

console.log(text);

So:

const file = await fileHandle.getFile();

const text = await file.text();

console.log(text);

Output:

Hello from OPFS!

You should memorize this conceptually:

navigator.storage.getDirectory()
            ↓
        root handle
            ↓
   getDirectoryHandle()
            ↓
      directory handle
            ↓
     getFileHandle()
            ↓
        file handle

13. Now IndexedDB

Let's do the same thing with IndexedDB.

Basic initialization:

const request = indexedDB.open("MediaManager", 1);

Here:

MediaManager

is our database.

The:

1

is the database version.

14. Creating an object store

IndexedDB has an interesting mechanism called:

onupgradeneeded

Example:

const request = indexedDB.open("MediaManager", 1);

request.onupgradeneeded = (event) => {

    const db = event.target.result;

    db.createObjectStore("files", {
        keyPath: "id"
    });
};

Now conceptually:

MediaManager
└── files

And every record will have:

id

as its key.

For example:

{
    id: "123",
    name: "video.mp4",
    size: 20000000
}
15. Adding data

IndexedDB uses transactions.

This is important.

const transaction = db.transaction(
    "files",
    "readwrite"
);

const store = transaction.objectStore("files");

store.add({
    id: "123",
    name: "video.mp4",
    size: 20000000,
    type: "video/mp4"
});

Conceptually:

Database
   ↓
Transaction
   ↓
Object Store
   ↓
add()
16. Reading data

For one record:

const transaction = db.transaction(
    "files",
    "readonly"
);

const store = transaction.objectStore("files");

const request = store.get("123");

request.onsuccess = () => {

    console.log(request.result);
};

Result:

{
    id: "123",
    name: "video.mp4",
    size: 20000000,
    type: "video/mp4"
}
17. Why IndexedDB feels annoying

You'll probably notice something:

const request = indexedDB.open(...)

Then:

request.onsuccess = ...
request.onerror = ...
request.onupgradeneeded = ...

It's an older browser API design.

That's why in our actual application, we'll create a small wrapper around IndexedDB.

Instead of writing this everywhere:

const transaction = db.transaction(...);
const store = transaction.objectStore(...);
...

we'll eventually be able to write:

await db.addFile(metadata);

Much cleaner.

But I don't want to hide IndexedDB behind a library initially.

You need to understand what the library is hiding.

18. The most important part: OPFS vs IndexedDB

This is where I want you to become very comfortable.

Imagine uploading:

lecture.mp4

Metadata:

{
    id: "abc123",
    name: "lecture.mp4",
    size: 250000000,
    type: "video/mp4",
    createdAt: 1720000000
}

This belongs in:

IndexedDB

The actual:

lecture.mp4

belongs in:

OPFS

So:

                    lecture.mp4
                         │
             ┌───────────┴───────────┐
             │                       │
         Metadata                 Actual data
             │                       │
             ▼                       ▼
        IndexedDB                   OPFS
             │                       │
             ▼                       ▼
        id = abc123            /files/abc123/
        name                   lecture.mp4
        size
        type
        createdAt
        opfsPath

That relationship is the core of our project.

This is a more advanced question that will come up later.

    name: "lecture.mp4",
    opfsPath: "files/abc123/lecture.mp4"

rather than making our entire architecture depend on passing handles around.

But we'll eventually learn:

These are exactly the details that become important when you encounter production OPFS code.
